## 1. 앱 한 줄 소개

> **차가 직접 쓰는 차계부.** 주행거리와 연료·배터리 사용량을 차량 데이터로 자동 기록해 소모품 교체 시점을 스스로 맞추고, 차량 내비에 주유소·충전소·정비소를 직접 끼워 넣는 차량 밀착형 차계부. 연료차와 전기차를 모두 지원한다.

## 2. 기획 배경

### 2.1 고객 니즈와 불편한 순간

차를 관리하고 싶은 운전자는 많지만, 관리를 계속하는 운전자는 적다. **기록이 귀찮기 때문이다.**

| 불편한 순간 | 지금 하는 일 | 결과 |
|---|---|---|
| 주유·충전을 마쳤을 때 | 영수증을 보고 금액·주유량·주행거리를 폰에 입력한다 | 몇 번 하다 그만둔다. 연비와 지출 통계가 틀어진다 |
| 정비소에 다녀왔을 때 | 정비 내역을 따로 입력해야 한다 | 대부분 남기지 않는다. 다음 교체 시점을 모른다 |
| 연료·배터리가 얼마 안 남았을 때 | 운전 중에 주유소를 찾아 내비를 다시 설정한다 | 주행 중 조작이 위험하고, 반대편이나 비싼 주유소에 들른다 |
| 사고가 났을 때 | 경황이 없어 보험사 번호를 찾는다 | 긴급출동 요청이 늦어진다 |
| 내 차 연비가 좋은 편인지 궁금할 때 | 비교할 기준이 없다 | 운전 습관을 바꿀 동기가 없다 |

시중 모바일 차계부 앱도 같은 한계를 보인다. 앱은 차의 주행거리를 알 수 없어서 **사용자에게 주기적으로 주행거리 입력 알림을 보내야만** 정비 주기를 계산할 수 있다. `[근거 필요: 앱 리뷰·시장 조사 같은 공개 자료의 입력률·이탈률 수치가 있으면 넣는다]`

### 2.2 해결 필요성: 왜 차 안이어야 하는가

모바일 차계부의 한계는 데이터가 사람 손을 거친다는 점이다. 차량 앱은 다르다.

- 총 주행거리, 배터리 에너지, 연료 잔량, 실측 연비를 **차가 알고 있다.** 에뮬레이터에서 총 주행거리를 바꾸면 앱이 바로 받는 것을 확인했다(실측).
- 엔진 이상, 오일류·타이어 경고, 에어백 전개를 **차가 먼저 안다.**
- 어디로 가는지, 언제 도착했는지를 **차량 내비가 안다.** 앱이 내비에 경유지를 넣으면 운전자 확인 없이 바로 경로에 들어간다(실측).

차곡은 이 데이터로 **기록을 자동화하고**, 기록이 필요한 순간과 정비·주유가 필요한 순간을 **이동 경로와 연결한다.**

## 3. 주요 기능 및 차량 특화 요소

### 3.1 기능 구성

**A. 자동 기록: 차가 쓰는 차계부**

| 기능 | 하는 일 | 차량 특화 요소 |
|---|---|---|
| 주행거리 자동 기록 | 시동이 걸리면 총 주행거리를 읽어 기록한다. 앱을 처음 켠 시점의 총 주행거리를 기준으로 삼고, 앱이 꺼져 있던 기간의 주행도 총 주행거리 차이로 이어 붙인다. 이전 기록은 모바일 차계부에서 가져온다 | Vehicle SDK 총 주행거리(실측), 부팅 시 백그라운드 서비스(실측) |
| **관리항목 주기 자동 갱신** | 엔진오일·필터·타이어·브레이크 등 소모품마다 마지막 교체 이후 주행거리와 기간으로 진행률을 계산한다. 주행거리가 자동으로 들어오므로 진행률이 실시간으로 맞고, 교체 시점 알림도 정확해진다. 연료차와 전기차는 관리항목이 다르다(전기차는 엔진오일·점화플러그가 없고 감속기오일·배터리 냉각수가 있다) | Vehicle SDK 총 주행거리 실시간 구독 |
| 연비·전비 기록 | 연료차는 차량이 측정한 연비를 쓰고, 전기차는 앱이 "주행거리 증가 ÷ 배터리 에너지 감소"로 직접 계산한다. 계기판 연비와 주유 기록으로 낸 실제 연비를 함께 보여 주고 차이를 알려 준다 | Vehicle SDK 연비, 배터리 에너지·용량(실측) |
| 공회전 분리 | 정차(차속 0) 상태로 기어 P·N이거나 브레이크를 밟고 서 있는 시간을 공회전으로 보고 따로 기록한다. 전기차는 정차 중 배터리 사용량을 직접 재서 "주행 전비"와 "전체 전비"를 나눠 보여 준다. 연료차는 공회전 시간과 추정 연료량만 보여 준다 | 차속, 기어, 브레이크(실측), 배터리 에너지 |
| 연비 원인 분석·개선 추천 | 순간 연비를 기록하면서 그 순간의 에어컨 사용, 제동 빈도, 급가속(차속 변화), 주행 모드, 정체 구간을 같이 저장해 "에어컨을 켠 구간 연비가 12% 낮아요", "정체 구간 18분 때문에 이번 주행 전비가 9% 떨어졌어요" 같은 원인과 방법을 알려 준다 | Vehicle SDK 공조·브레이크(실측), AAOS 차속, NaviHelper 정체 구간(실측) |
| 주유·충전 기록 안내 | 연료차는 주유 후 거리 초기화와 연료 증가로, 전기차는 충전구 열림과 배터리 증가로 주유·충전을 감지한다. 위치로 주유소·충전소를 찾고 단가로 금액을 미리 채운다. 운전자는 확인만 누른다 | Vehicle SDK 연료 %·주유 후 거리, 충전구·배터리(실측), NaviHelper 현재 위치(실측), 오피넷·충전소 공공 API |
| 운행 기록·통행료 | 목적지마다 거리·시간·통행료·효율을 기록한다. 통행료는 내비가 경로 시작 때 알려 주는 예상 통행료로 채운다 | NaviHelper 경로 시작(통행료)·도착 이벤트(실측) |
| 음성 기록(Gleo) | "엔진오일 교체 8만 원 기록해 줘"처럼 말로 기록한다. Gleo에 등록할 수 있는 함수는 최대 3개라서 손을 쓰기 어려운 기능부터 고른다. 후보: 지출 기록, 주유소·충전소 경유지 추가, 워키토키 보내기 `[결정 필요]` | Gleo 앱 함수 호출(에뮬레이터에 Gleo와 같은 방식을 쓰는 내비 앱이 있음. 3rd-party 등록 가능 여부는 설명회 확인). 대체: 앱 마이크(실측) + 음성인식 |

| 기능 | 하는 일 | 차량 특화 요소 |
|---|---|---|

### 3.2 주행 중과 정차 중

앱 카테고리는 **Mobility Services**다. 카테고리 정책이 주행 중 허용 예시로 드는 "주행과 관련된 차량 관리", "주유소 탐색"에 맞춰 주행 중에는 최소한의 기능만 연다.

| 상황 | 쓸 수 있는 기능 | 방식 |
|---|---|---|
| 주행 중 | 주유소·충전소 경유 제안, 경고·사고 알림, 워키토키 `[결정 필요]` | 큰 카드 한 장과 버튼 두 개("들르기 / 나중에"). 키보드 입력 없음. 워키토키는 화면 터치 없이 자동 답장 창과 음성 호출로만 쓴다. 사람 간 소통은 Mobility Services의 주행 중 허용 예시에 없어서 설명회에서 확인한다 |
| 주행 시작 직후 | 주유·충전·정비 기록 확인 | 프리셋 선택 한 번 |
| 정차 중 | 기록 수정, 통계, 순위, 커뮤니티, 설정 | 전체 화면 |

| | 모바일 차계부 | 차곡 |

| 비교 | 없음 | 같은 차종 통계·순위 |

## 4. 주요 사용 시나리오

### 시나리오 A. 출퇴근 직장인: "배터리가 부족할 때, 가는 길에 충전하고 자동 기록"

- **누가**: 30대 직장인, 전기차 운전자. 차계부 앱을 깔았다가 한 달 만에 그만둔 경험이 있다.
- **상황**: 퇴근길, 내비로 집까지 안내받는 중에 남은 주행거리가 기준 아래로 떨어졌다.
- **흐름**
  1. 주행 중 카드 한 장이 뜬다. "충전소 들르면 4분 더 걸려요. 도착 시 배터리 18% 예상. 들를까요?" [들르기] [나중에]
  2. [들르기]를 누르면 진행 방향 오른쪽 충전소가 내비 경유지로 들어간다.
  3. 충전구가 열리고 배터리가 오르면 차곡이 충전을 감지한다. "32kWh, 약 1만 1천 원. 기록할까요?" [확인]
  4. 월말에 지출, 공회전을 뺀 주행 전비, 같은 차종 평균과의 비교, 전비를 떨어뜨린 원인(에어컨, 정체 구간)이 자동으로 정리된다.
- **사용 API**: Vehicle(총 주행거리, 배터리 에너지·잔량, 충전구), NaviHelper(경유지 추가, 현재 위치·진행 방향, 도착 예상 잔여 에너지), 외부 길찾기·충전소 API
- 연료차도 같은 흐름이다. 주유소와 오피넷 단가를 쓴다.

### 시나리오 B. 정비소 방문: "다녀오기만 하면 기록이 남는다"

- **누가**: 40대 운전자. 엔진오일 교체 시기를 늘 놓친다.
- **상황**: 차곡이 엔진오일 교체 주기 도달과 엔진오일 레벨 경고를 함께 알렸다.
- **흐름**
  1. 정차 중 "엔진오일 교체 시기입니다" 카드에서 [가까운 블루핸즈]를 누른다. 예약 페이지가 열리고, 정비소가 내비 목적지로 설정된다.
  2. 정비소에 도착하면 차곡이 도착을 기억한다.
  3. 정비 후 다시 출발하면 "엔진오일을 교체하셨나요?" [교체함] [다른 정비] [안 함]
  4. [교체함] 한 번으로 정비 기록과 다음 교체 시점이 갱신된다.
- **사용 API**: Vehicle(엔진오일 레벨, 총 주행거리, 기어), NaviHelper(목적지 설정, 목적지 정보, 도착 이벤트)

### 시나리오 C. 사고 순간: "경황이 없어도 다음 할 일이 보인다"

- **누가**: 운전 경력 2년 차 운전자.
- **상황**: 교차로에서 추돌 사고가 나 에어백이 터졌다.
- **흐름**
  1. 차곡이 에어백 전개를 감지하고 화면에 사고 대응 카드를 띄운다. "보험사 긴급출동: ○○손해보험 1588-XXXX"
  2. 2차 사고 예방(비상등, 안전한 곳으로 대피), 사진 촬영 등 대응 순서를 큰 글자로 보여 준다.
  3. 사고 시각과 위치, 주행거리가 차계부에 사고 기록으로 남는다.
- **사용 API**: Vehicle(에어백 전개, 총 주행거리), NaviHelper(현재 위치)

### 시나리오 D. 법인 차량: "운행일지가 저절로 쌓인다"

- **누가**: 영업용 차량 10대를 운영하는 회사의 차량 담당자와 운전자.
- **흐름**
  1. 담당자가 소속 차량에 차곡을 설치하고 법인 차량으로 등록한다.
  2. 운전자는 평소처럼 운전한다. 목적지마다 거리·시간·통행료가 자동으로 쌓인다.
  3. 월말에 차량별 운행일지와 주유·충전·통행료 지출이 비용 정산 자료로 정리된다.
- **사용 API**: Vehicle(총 주행거리, 배터리·연료), NaviHelper(경로 시작·도착 이벤트)

## 5. 개발 계획

### 5.1 Pleos Connect 환경에서의 구현 방법

```
차량 (Pleos Connect, AAOS)
  차곡 앱 (Kotlin, Jetpack Compose, MVI)
    ├─ Vehicle SDK      총 주행거리·배터리·연료·연비·공조·브레이크·기어·안전 경고·VIN
    ├─ NaviHelper SDK   목적지·경유지 설정, 경로 시작·도착 이벤트, 회전 안내, 정체 구간, 현재 위치·진행 방향
    ├─ Gleo 앱 연동      음성 기록 함수 호출 (조건부)
    ├─ AAOS Car API     차속, 오디오 포커스
    ├─ 기록 서비스        부팅 시 시작, 주행거리·에너지 스냅샷 (정책 확인 후 상주 범위 결정)
    └─ Room DB          기록 저장. 오프라인에서도 핵심 기능 동작
          │ HTTPS (동의한 경우만, 가명화한 요약값)
백엔드 (NestJS, PostgreSQL, Redis)
    차종별 통계·순위, 커뮤니티, 워키토키 음성 중계, 유가·주유소·충전소 캐시, 길찾기 호출
```

- **연료차·전기차**: 차량에 에너지 종류를 두고 처음부터 데이터 구조에 넣는다. 주유와 충전은 "에너지 기록" 하나로 묶는다. 감지 방식, 효율 계산, 관리항목 목록, 주유소·충전소만 나뉜다.
- **기록 시점**: 부팅 시 백그라운드 서비스로 주행거리·에너지 스냅샷을 찍는다(실측). 화면은 자동으로 띄울 수 없어서(실측) 알림으로 연다. 앱이 꺼져 있던 동안은 누적값 차이로 합계를 복원한다. 운전습관·공회전처럼 촘촘한 수집은 앱을 띄워 둔 주행에서만 한다.
- **주행 안전**: 주행 중에는 `CarUxRestrictions`를 따라 경고·경유지 카드만 보여 준다. 키보드 입력과 화면 터치 위주의 기능은 정차 중에만 쓴다.
- **차종 호환**: 모델명으로 분기하지 않고 `checkXxxCapabilities`로 지원 여부를 확인한다. 지원하지 않는 기능은 숨긴다. 공조는 차량이 지원하는 좌석 영역으로 부른다(실측: 실내 전체 영역 `0x75`).
- **리소스**: 주행 중 CPU 5% 미만, RAM 400MB 이하를 지킨다. 백그라운드에서는 스냅샷만 찍고 바로 끝낸다.
- **개인정보**: 차량 데이터는 기기 안에 저장한다. 서버로는 동의한 사용자의 가명화한 요약값(차종, 월 평균 효율)만 보낸다. 주행 데이터는 마케팅에 쓰지 않는다. 대여 모드에서는 개인 기록을 숨긴다.

### 5.2 UI 설계 원칙

Pleos Connect UI 디자인 가이드를 따른다.

- 모든 화면을 Portrait(1창)와 Landscape(2창) 두 레이아웃으로 만든다. Landscape에서는 기록 목록과 상세를 나란히 보여 준다.
- Light·Dark 테마를 모두 지원하고, 색은 Pleos 디자인 토큰만 쓴다.
- 버튼, 팝업, 토스트, 탭은 Pleos 컴포넌트를 쓴다. 본문은 최소 26 크기로, 핵심 정보는 1~2초 안에 읽히게 한다.
- 주행 중 카드는 정보 한 줄과 버튼 두 개로 제한하고, 장식 애니메이션을 쓰지 않는다.

### 6.2 예상 MAU와 Retention `[근거 필요]`

- **MAU 산식**: Pleos Connect 탑재 차량 수 `[근거 필요]` × 앱 설치율 `[가정]` × 월 1회 이상 실행률 `[가정]`
- **Retention이 높은 이유**
  - 사용자가 아무것도 하지 않아도 기록이 쌓인다. 모바일 차계부의 이탈 원인인 "입력 피로"가 구조적으로 없다.
  - 주유·충전(평균 1~2주 주기)과 정비 같은 반복 이벤트가 앱을 다시 열게 만든다.
  - 같은 차종 순위와 워키토키 그룹이 기록 외의 재방문 동기를 만든다.
  - 목표: 30일 Retention `[근거 필요: 공개된 차량 관리·차계부 앱의 Retention 수치와 비교]`

### 6.3 확대 계획

1. **Pleos API 개방과 함께 넓히기**: 개발하며 필요했지만 지금은 열려 있지 않은 기능을 [API 개방 제안](PLEOS_API_PROPOSAL.md)으로 정리했다. 예를 들어 하이패스 거래가 열리면 예상 통행료 대신 실제 결제 금액이 기록되고, 시동 이벤트가 열리면 주행 시작을 더 정확하게 잡는다.
2. **차량 스킨과 실내 무드등 테마**: 내 차종을 닮은 미니카에 색·스티커·전개도 랩을 입히고, 스킨마다 정한 실내 앰비언트 조명 색을 실제 차에 적용한다. 법인은 회사 로고 랩과 회사 색 조명을 소속 차량에 배포한다. 시제품을 만들었고(조명 명령은 에뮬레이터에서 차량 HAL 전달까지 확인), 탑재 차종의 3D 에셋을 확보하거나 Pleos가 주행 화면 차량 테마를 열면 넣는다.
3. **정비 예약 직접 연동**: 오토큐·블루핸즈 예약 시스템과 연동해 앱 안에서 예약을 끝낸다.
4. **보험 연계**: 차량이 기록한 실제 주행거리로 마일리지 특약 할인을 쉽게 받게 한다(사용자 동의 기반).
5. **법인 차량 관리(B2B)**: 운행일지, 비용 정산, 회사 스킨 배포를 묶어 법인용으로 제공한다.
6. **빌트인캠 연동**: 차량 블랙박스 API가 공개되면 사고 기록에 영상 구간을 붙인다.

**팀 기능안에서 바꾸거나 뺀 것** (근거: [기획 기반 정리 §4.3](PLANNING_FOUNDATION.md), [조사 노트 §11](PLEOS_PLATFORM_RESEARCH.md))

| 원래 기능안 | 초안 반영 | 이유 |
|---|---|---|
| 빌트인캠 사고 영상 기록 | 사고 데이터 기록으로 바꾸고 영상은 확장 계획으로 | 차량 앱용 카메라·블랙박스 API가 없다 |
| Gleo 음성 변환 데이터 수신 | "Gleo 앱 함수 호출"로 표현을 바꾸고 조건부로 둠 | Gleo는 음성 원문을 넘기지 않는다. Gleo 앱 연동 권한 일부가 시스템 전용이다 |
| 이전 주행거리 기록 호출 | 처음 켠 시점 기준 + 누적값 차이로 합계 복원 + 모바일 차계부 가져오기 | 과거 주행 이력을 주는 API가 없다 |
| 주유소 체류 시간으로 주유 감지 | 연료·배터리 신호로 감지하고 위치는 주유소 확인용으로만 씀 | 차량 신호가 더 정확하다 |
| 경로 기록, 경로 받아서 주유소 찾기 | 운행 단위 기록 + "우리가 고른 주유소를 내비에 끼워 넣기" | 경로 선(폴리라인)은 받을 수 없다. 경유지 보내기는 확인창 없이 된다 |
| 차량 진단 결과 | 쓸 수 있는 경고 6종으로 한정 | 고장 코드와 경고등 묶음은 시스템 앱 전용이다 |
| 차량 3D 스킨, 스킨 마켓, 실내 무드등 | 본 기능에서 빼고 확대 계획 2번으로 보류(2026-10-26) | 주행 화면 3D 차량은 시스템 앱 전용이다. 앱 속 3D는 실차 특징을 살린 모델을 무료로 구할 수 없고(실차 모델은 유료·보도용 제한, 직접 만든 미니카는 닮음이 부족), 차계부 핵심과 거리가 멀다. 시제품과 조사 결과는 [archive/skin-prototype](../archive/skin-prototype/README.md) |
| 워키토키 핸들 버튼 누르고 말하기 | 자동 답장 창 + Gleo 호출, 핸들 키는 개방 시 | 핸들 키는 앱이 화면 앞에 있을 때만 받는다. 사용자 지정 키 경로가 없다 |
| 하이패스 통행료 자동 기록 | 내비 예상 통행료 | 하이패스 거래를 읽는 API가 없다 |
| 시동 감지 | 기어·주행거리·부팅 신호 조합 | 시동 상태를 주는 API가 없다 |
| 전기차 확장(확대 계획) | 본 기능으로 당김 | 에뮬레이터 차량이 전기차라 실제 신호 시연이 전기차로만 된다 |

**팀이 정할 것**: 앱 이름, 부문(대학생/일반), 대여 모드의 정확한 정의, Gleo 함수 3개, 워키토키 주행 중 허용 여부, 외부 길찾기 API, 1차 제출까지의 기능 범위

**채울 것**: 탑재 차량 수, 모바일 차계부 앱의 입력률·이탈률(공개 자료 범위에서), 화면 시안

**확인할 것**: 관리항목 주기·차종 제원의 공개 출처([기획 기반 정리 §2.5](PLANNING_FOUNDATION.md)), 10-28 설명회 질문([조사 노트 §12](PLEOS_PLATFORM_RESEARCH.md), [API 개방 제안](PLEOS_API_PROPOSAL.md))
